**The result worth knowing: EKF3 fuses our ExternalNav fixes.** ArduCopter built
from source for SITL, GPS disabled at runtime, a position injected 20 m north at
4 Hz. The estimator walked to 19.81 m of the 20 m inside 5 seconds and held it.
`check_extnav.py` passes all four stages and all twelve parameters. The MAVLink
write path is settled; stop treating it as a risk.

Two limits on that run, both in the results file: the `ekf flags` column read
0x00000000 throughout because the EXTENDED_STATUS request did not deliver
`EKF_STATUS_REPORT`, so it is decoration rather than evidence; and SITL shares
ArduPilot's estimator and MAVLink handler but not the serial link, the timing or
the camera.

`configs/flight.yaml` also moved to `fps: auto`, so the Pi cannot silently
inherit the Xavier's hand-tuned feed rate. The Pacer and
`scripts/feed_fps_sweep.sh` were already built; the fps work is done, not open.

### Reproducing the SITL rig

```
git clone --depth 1 --recurse-submodules --shallow-submodules https://github.com/ArduPilot/ardupilot
cd ardupilot && ./waf configure --board sitl && ./waf copter        # 1429 targets, 7m30s
build/sitl/bin/arducopter -S -I0 --model quad --speedup 5 \
    --defaults Tools/autotest/default_params/copter.parm,extnav.parm --sysid 1
python scripts/check_extnav.py --endpoint tcp:127.0.0.1:5760
python scripts/watch_extnav.py  --endpoint tcp:127.0.0.1:5760 --offset-m 20
```

`extnav.parm` is the block in the `configs/flight.yaml` header. Three traps
already paid for:

- **`empy==3.3.4` will not build a wheel on Python 3.11+.** `pip download` the
  sdist and copy `em.py` into site-packages. `pexpect` is also required.
- **Do not put `GPS1_TYPE 0` in the defaults.** The EKF then never takes an
  origin and `check_extnav.py` stops at stage 3, correctly. Boot with GPS, let
  the origin establish, then set `GPS1_TYPE 0` at runtime, which is what
  `watch_extnav.py` does.
- Backgrounded processes are reaped between tool calls in some environments.
  Start SITL and run the client in one shell invocation.

## Work, in order

### 1. `geoanchor-logs` on GitHub

`https://github.com/Saikrishna-Bulusu/geoanchor-logs` is private and was
unreachable. The material is `geoanchor-rt/runs/`, 41 runs named
`<UTC stamp>_<tag>`, each carrying `session.json` (keys: schema, header,
summary, records, layers, logs, codes, map, basemap) plus per-layer `.jsonl`
and `.out`.

Segregate by **board** then **method**, which is the comparison the paper makes:
`board/<pi5|xavier|legion>/<method>/<stamp>_<tag>/`. `session.json.header`
carries the board and the method, so the sort is mechanical rather than a
judgement call. Write the README against what `git ls-files` actually shows, and
cover: what a run is, what each file in it holds, what `session.json.summary`
means, which runs are synthetic-fixture (timing only, accuracy meaningless) and
which are env80 (real ground truth). Mark the Sydney replay runs clearly — the
frames are cut from the reference tile, so their 0.007 m is a wiring proof and
must never be quoted as accuracy.

Do not commit weights, stores, tiles or `node_modules`. Esri Wayback imagery is
measurement-only working data and should not be redistributed; NSW imagery is
CC BY and needs attribution if it goes up.

### 2. PX4

`PX4-Autopilot` v1.16.2 is already built at `build/px4_sitl_default` and
`Micro-XRCE-DDS-Agent` is built. Untested here only because the sandbox lacked
`libgz-transport13.so.13`.

`fcout.py` already speaks both `ODOMETRY` and `VISION_POSITION_ESTIMATE` and
carries a `firmware` field, so the code probably needs nothing. What differs is
the parameter set: PX4 wants `EKF2_EV_CTRL`, `EKF2_HGT_REF`, `EKF2_EV_DELAY`
rather than the `VISO_*` and `EK3_SRC1_*` block. `check_extnav.py`'s `WANT`
table is ArduPilot-only and needs a PX4 branch. Then run the same two-stage
test: parameters, then `watch_extnav.py` with GPS off, and report whether PX4's
EKF2 walks to the injected position the way EKF3 did.

Decide deliberately whether PX4 goes over MAVLink or over uXRCE-DDS. MAVLink
reuses everything already verified. DDS is the modern PX4 path and is what NGPS
uses through ROS 2, but it is a second write path to get right and nothing in
this repo speaks it yet.

### 3. RIPE++

`https://github.com/fraunhoferhhi/RIPEpp`, ECCV 2026 LIMIT workshop,
arXiv 2608.19693. Ships three pretrained checkpoints (MegaDepth, SCARED,
Aachen) and builds with `uv sync`, so integration is inference-only.

It is more interesting than a ninth row. It learns from positive image pairs
only, with no correspondence labels, and it ships a **trainable matcher**, which
is the thing that makes a fine-tune viable here: a fine-tuned XFeat descriptor
breaks LighterGlue, because LighterGlue's first layer was fitted to XFeat's
descriptor basis. RIPE++ brings its own matcher and sidesteps that.

Register it as a method the way XFeat and EdgePoint2 were, run env80 satellite
first, and check the licence before it reaches anything shippable.

### 4. Cross-date, other Australian cities

Already built and already measured over Sydney: `scripts/fetch_wayback_tile.py`,
`scripts/crossdate_probe.py`, curve in `results/crossdate_wayback_curve.md`.
**There is a sharp cliff at 3 years** — 20 to 31 inliers and 3.3 to 7.9 m median
inside it, 5 inliers and 0 to 2 of 24 solved past it. A 6 to 7 year gap is a
known-failure condition, not a benchmark.

The open question is whether the 3-year cliff is a property of the matcher or an
artefact of the Sydney CBD. Re-run the same probe over Melbourne, Brisbane,
Perth and one rural area at 0 to 3 year gaps. Wayback is global and needs no
token. **Always run the same-tile control** — without it a zero-fix result is
indistinguishable from a broken harness — and hold resolution constant at one
zoom, because resolution is a confound that hides the cliff.

### 5. top_k

`results/topk_sweep/` has k512, k1024, k2048, k4096 and `topk_sweep_ep2/` is
empty. Check what the first sweep actually covers before re-running it: if it is
latency-only, the missing half is accuracy on env80 per k, which is what turns
it into a Pareto front. `scripts/topk_pareto.sh` exists.

### 6. `/ponytail:ponytail-review`

Worth doing for portability across four boards, **not as a latency strategy**.
The measured split is compute 411.7 ms of a 579.4 ms latency, transport 1.22 ms,
`json.dumps` 0.028 ms. A code cleanup targets half a percent of the budget. The
levers that reach the 250 ms budget are frame pixels (0.55 scale took the Xavier
from 342.8 to 238.0 ms), tile count through the prior, and top_k.

### 7. Dashboard, then the report

Next.js 14 at `dashboard/`, static export. Once the logs are organised, point it
at the new layout and open it on one cross-date run against a real reference
tile, not a Sydney replay, so what renders is a genuine fix.

The methods report comes last because it needs every number above.
`results/env80_sweep/summary.json` plus `classical_baselines_env80.txt` already
cover orb, sift, akaze, xfeat_mnn and xfeat_lg on both scenes, so the table is
mostly assembly rather than new runs.

## Standing rules that bite on this work

From CLAUDE.md, repeated because each one has already cost time:

- **Never quote the mean.** Satellite runs contain fixes wrong by 2.06e93 m.
  Median, p90, p99 and the fraction inside 5/10/20 m.
- **`PDE`, `R_i`, `pdm_at_k`, `recall_at_k`, `retrieval_gt_rank`, `pred_error`,
  `location_error_list`, `truePos.*` are ground truth and may never be
  predictors.**
- Cross-validate grouped by scene, never by row.
- Exclude `Scene_21` from every estimator number and report it separately. It is
  a matcher failure, not a localisation result.
- Any descriptor fine-tune uses XFeat, never SuperPoint. The Magic Leap licence
  assigns derivatives to Magic Leap.
- One runnable script, never a code block mixing `#` comments and commands.
- `rsync` to the Pi with the `--exclude` list intact. `.git`, `results/` and
  `avl-bench/results/` exist only on the Pi and `--delete` without them has
  already destroyed two transcripts and the git history once.
