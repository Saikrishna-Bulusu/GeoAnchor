# RIPE++ on env80: zero fixes, and the control says that is real

Measured 17 Sept 2026 on the Legion, CPU only.
`https://github.com/fraunhoferhhi/RIPEpp`, LIMIT@ECCV 2026, arXiv 2608.19693,
default (MegaDepth) checkpoint, `max_keypoints` 2048.

Registered as `ripepp` / `ripepp_tokyo` / `ripepp_scared` in
`geoanchor/methods.py`, matched with the same mutual-nearest-neighbour
reduction every other learned method here uses, so the comparison isolates the
descriptor rather than the matcher.

---

## Licence: this one can be measured and can never ship

RIPE++ is **not** open source. It ships under Fraunhofer's *Software Copyright
License for Academic Use*, which permits "non-commercial purposes of
evaluation, testing and academic research" and prohibits commercial use or

Every other matcher in this project is permissive — XFeat Apache 2.0,
EdgePoint2 MIT, SIFT/ORB/AKAZE inside OpenCV. RIPE++ is the first that is a
benchmark reference point rather than a candidate. That is a licence fact, not
a performance judgement, and it holds regardless of the numbers below.

## The result

`results/ripepp_env80/summary.json`, Scene_09, satellite reference, 25 frames,
cold start:

| | |
|---|---|
| frames | 25 |
| **plausible solves** | **0** |
| accept rate at any gate | 0% |
| median latency | **9 681 ms** |
| p95 latency | 16 256 ms |

Zero. Not "low" — none at all.

## The control, which is what makes that reportable

This project's own rule, from the cross-date work: *a zero-fix result is
indistinguishable from a broken harness without a control.* So RIPE++ was run
against a copy of the same tile, the trivial task, alongside EdgePoint2 as a
reference point:

| matcher | median inliers | solved | median error |
|---|---|---|---|
| **RIPE++ (MegaDepth)** | **112** | **6/6** | **0.000 m** |
| EdgePoint2 Small (64-D) | 93 | 6/6 | 0.029 m |

`results/ripepp_control.json`. **The adapter works, and RIPE++ is the stronger
of the two on self-matching** — more inliers and a lower error than the method
this project currently ships.

So the env80 zero is a genuine transfer failure, not a wiring fault. RIPE++
matches a picture to itself better than EdgePoint2 does, and fails completely
on a real UAV frame against a satellite basemap.

That is not surprising once stated: all three published checkpoints are
MegaDepth (ground-level internet photo collections), MegaDepth + Tokyo 24/7,
and SCARED (endoscopy). **None is aerial, and none is cross-view.** Aerial-to-
satellite is a viewpoint change no checkpoint here has seen.

## The compute cost rules it out independently

Same frame (646×484), 4 threads, warm, median of 5:

| method | detect | match (self) | keypoints | descriptor |
|---|---|---|---|---|
| `xfeat_mnn` | **34.3 ms** | 5.5 ms | 2048 | 64-D |
| `edgepoint2_s64` | **32.0 ms** | 4.8 ms | 2048 | 64-D |
| `ripepp` | **2 666 ms** | 12.8 ms | 2048 | **256-D** |

**78× XFeat's detection cost**, on a laptop. The backbone is **VGG19-BN** —
548 MB of ImageNet weights — where XFeat is a small purpose-built CNN and
EdgePoint2's largest variant is a few hundred kilobytes. For a project whose
binding constraint is a 250 ms budget on a CPU-only embedded board, that is
disqualifying on its own.

The 256-D descriptor is a second, smaller problem: it quadruples the reference
feature store on disk and in RAM against the 64-D methods, and the match cost
is linear in descriptor width.

## What was still worth learning

The handoff's reason for trying RIPE++ was not that it would be a ninth row. It
learns from **positive image pairs only**, with no correspondence labels, and
it ships a **trainable matcher** — which is the one path to a fine-tuned
descriptor that does not break its own matcher. Fine-tuning XFeat's descriptor
breaks LighterGlue, because LighterGlue's first layer was fitted to XFeat's
descriptor basis, so the accuracy leader and the fine-tuning path are mutually
exclusive in the current lineup.

That argument survives this result, and is now better supported than before:
the control shows RIPE++'s descriptor is genuinely strong where it has been
trained. What it lacks is aerial training data, which is the thing this project
has and the checkpoints do not.

So the honest reading is **not** "RIPE++ does not work". It is:

- As a **matcher to deploy**: ruled out twice over, by licence and by a VGG19
  backbone at 78× the detection budget.
- As a **fine-tuning vehicle**: still the most interesting option on the table,
  and it would need training on aerial-to-satellite pairs before any env80
  number from it means anything. The label-free positive-pairs-only training is
  what makes that plausible with the data this project actually has.
- The **Tokyo 24/7 checkpoint** is untested here and is the only published one
  trained for appearance change over time, which is the nearest analogue to the
  cross-date problem. Cheap to try; the same compute and licence limits apply.

## Reproduce

```bash
git clone https://github.com/fraunhoferhhi/RIPEpp.git ripepp
python scripts/env80_sweep.py --methods ripepp --scenes Scene_09 \
    --out results/ripepp_env80 --limit 25 --frame-keypoints 2048 --ref-keypoints 2048
python scripts/crossdate_probe.py --query <a tile> --methods ripepp,edgepoint2_s64 \
    --frames 6 --max-keypoints 2048 --gate 8 --json results/ripepp_control.json
```

The checkpoint downloads from `cvg.hhi.fraunhofer.de` on first use. **That
server serves a broken TLS chain** — its leaf is signed by GEANT TLS ECC 1 and
it presents the RSA intermediate instead — so `urllib` and `curl` both refuse
it. The correct intermediate is fetched from the certificate's own AIA URL
(`http://crt.harica.gr/HARICA-GEANT-TLS-E1.cer`) and verifies against the
HARICA ECC root already in the system store. Do not disable verification to
work around it.

`ripepp/` is gitignored: third party, and under a licence that should not enter
this repo's history. Set `RIPEPP_ROOT` if you keep it elsewhere.
