# The pipeline's fixes reach PX4's EKF2, over DDS, at the pipeline's own rate

17 Sept 2026, Legion. Full chain, nothing stubbed:

```
processing layer  --ZeroMQ-->  scripts/agp_bridge.py  --DDS-->  MicroXRCEAgent
                                                                      |
                                                            uxrce_dds_client
                                                                      |
                                                       EKF2 aux global position
```

Reproduce:

```bash
source /opt/ros/jazzy/setup.bash
source ~/GeoAnchor/ros2_ws/install/setup.bash
MicroXRCEAgent udp4 -p 8888 &
# boot PX4 SITL, apply configs/px4_agp.params, reboot
GEOANCHOR_SET="data_layer.feed.loop=true" bash run.sh --no-api &
python scripts/agp_bridge.py
```

## What it showed

**AGP activated and consumed our fixes.** After 296 messages from the bridge:

```
estimator_aid_src_aux_global_position
    observation:          [-33.869890, 151.208930]   <- our Sydney fixes, intact
    observation_variance: [64.00000, 64.00000]       <- our eph of 8.0 m, squared
cs_aux_gpos: True                                    <- AGP control engaged
```

Three things are established by those three lines:

1. **The DDS route works end to end.** Fixes computed by the processing layer
   crossed the ZeroMQ bus, a ROS 2 publisher, the uXRCE-DDS agent, PX4's DDS
   client, and arrived in EKF2's aid source with their coordinates unchanged.
2. **The covariance arrives exactly, as one scalar.** `eph` 8.0 m in,
   `observation_variance` 64.0 out — 8.0². No packing, no per-axis-versus-summed
   question, no firmware-dependent layout. `EKF2_AGP_NOISE` was 0.1 so nothing
   was floored. This is the thing the external-vision path makes hard and this
   path makes trivial.
3. **`cs_aux_gpos: True` with GNSS denied.** EKF2 reset its horizontal position
   to our fix and then began gating subsequent ones, which is the documented
   `startEvPosFusion`-equivalent behaviour for AGP when no other horizontal
   source is aiding.

## Two things about this run that are NOT results

**The 9 046 km "drift" is the fixture, not an error.** PX4 SITL boots at its
default home in Switzerland; the Sydney replay produces fixes over the Sydney
CBD. EKF2 correctly reset 9 000 km to where we told it it was. Set
`PX4_HOME_LAT=-33.8687997 PX4_HOME_LON=151.2093` to co-locate them before
reading any distance from this rig.

**`innovation_rejected: True` on the longitude axis is also the fixture.** The
innovation was 97 m against a 3-sigma gate. `demo/flight.mp4` sweeps across the
reference tile at **85.6 m/s** — 21.4 m between frames — while the SIH vehicle
sits still, so the fix stream walks east and the vehicle does not. `CLAUDE.md`
already warns that this feed's dynamics are synthetic and must not be tuned
against. The latitude axis, where the sweep does not move, had
`test_ratio 0.003` and passed comfortably.

A meaningful accuracy number from this path needs a feed whose motion matches
the simulated vehicle's. That is a rig to build, not a number to quote.

## Why this path rather than external vision

`docs/px4_ekf2_extnav_2026-09-17.md` has the full comparison. In short:

| | EV over MAVLink | AGP over DDS |
|---|---|---|
| rate floor | **5 Hz**, silent below it | **none** (5 s timeout) |
| covariance | 21 floats, layout differs per firmware | `eph`, one scalar |
| frame | `LOCAL_FRD` only, rotated if no yaw claimed | lat/lon, no frame |
| origin | must match the EKF's, silently offset if not | none |
| new stack on the board | none | **ROS 2 + px4_msgs** |

The measured pipeline runs at 0.4–2.6 Hz depending on board and matcher, which
is below the EV floor almost everywhere. AGP has no floor.

**The bridge is a bridge, not a layer.** `scripts/agp_bridge.py` subscribes to
the processing layer's PUB socket exactly as `geoanchor/api` does, and nothing
in `geoanchor/` imports it. A board flying ArduPilot never runs it, and never
installs ROS. That is what keeps "no ROS in the pipeline" true while still
reaching the one PX4 aid source this pipeline's rate can satisfy.

## The alternative, which also works

Padding the MAVLink EV stream — compute slowly, re-send the most recent fix to
hold the rate above the floor — was measured and **does work**:

| | drift of 20 m | fused |
|---|---|---|
| 2.4 Hz, no padding | −0.01 m | no |
| 2.4 Hz fixes sent at 8 Hz, capture stamps | 20.27 m | **yes** |
| 2.4 Hz fixes sent at 8 Hz, restamped now | 20.27 m | **yes** |
| 2.0 Hz fixes sent at 6 Hz, capture stamps | 20.17 m | **yes** |

`scripts/watch_extnav.py --rate 8 --fix-rate 2.4`. It needs no new stack, and
it keeps all three EV encoding traps plus a filter being handed the same
observation two or three times. Kept on the record as the fallback for a board
where ROS 2 is not wanted.
